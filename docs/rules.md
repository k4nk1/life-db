# LifeDB 開発ルール

## 設計ドキュメント

### 保存場所とフォーマット

| ドキュメント | パス | 形式 |
|---|---|---|
| 機能要件 | `specification.md` | Markdown |
| 開発ルール | `docs/rules.md` | Markdown |
| Git運用 | `docs/git.md` | Markdown |
| テーブル定義 | `docs/db.md` | Markdown（テーブルごとにセクション分け） |
| API仕様 | `docs/api/<機能名>.md` | Markdown（エンドポイントごとにセクション分け） |
| ディレクトリ構成 | `docs/structure.md` | Markdown |

### ドキュメントの方針
- 必要最小限の記述にとどめ、トークンの浪費を避ける
- 実装時に参照するための仕様書として機能すればよい

---

## 設計方針

### 変更しやすい設計
- **バックエンド**：機能ごとにディレクトリを分離し、機能間の依存を最小限にする
- **フロントエンド**：画面ごとにコンポーネントを分離し、共通UIは共有コンポーネントとして切り出す
- **DB**：テーブル定義変更時はマイグレーションファイルで対応する。破壊的変更の場合はデータをエクスポート → DB再作成 → バッチスクリプトでインポートの手順を取る
- **API**：RESTful設計に従い、エンドポイントは機能単位でグループ化する

### UIコンポーネントライブラリ
- フレームワーク選定時にUIライブラリを確定する
- 全画面でそのライブラリの標準コンポーネントを使用し、カスタムCSSは最小限にする
- 独自デザインが必要な場合もライブラリのテーマ機能で統一する

---

## 実装ルール

### 全般
- ライブラリや既存コードを積極的に再利用し、車輪の再発明を避ける
- AI特有の過剰な装飾・コメント・抽象化を行わない
- フールプルーフや例外処理を細かく行わない（個人利用のため、問題発生時に修正する）

### テスト方針
- ロジック（処理の分岐など）ごとに正常系テストを1件実施する
- 通常発生しない操作（存在しないものの削除、マイナス数値の入力等）のテストは不要

---

## 実装順序

1. デイリー（タイプ管理含む）
2. やること
3. 事実＆思考
4. やらないこと
5. 文書管理
6. 資産
7. ホーム

各機能はバックエンド → フロントエンドの順で実装する。

### バックエンド実装フロー
1. 機能のディレクトリ・仕様を参照し、実装する関数を決める
2. 実装する
3. テストを作成・実行し、正常動作を確認する

### フロントエンド実装フロー
1. 機能のディレクトリ・仕様を参照し、実装する関数を決める
2. 動作するプロトタイプを作成し、ユーザーが確認する
3. 実装する
4. テストを作成し、ユーザーがテストを行い正常動作を確認する

---

## 仕様補足

- **タイムライン操作**：ドラッグ移動・伸縮・スナップに対応するライブラリを探し、なければ後回しにする
